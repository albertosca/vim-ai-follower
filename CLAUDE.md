# vim-ai-follower — notes for Claude Code

Live "follower" editor for Claude Code: `PreToolUse`/`PostToolUse` hooks (`claude-follow hook pre|post`) snapshot a file, diff it, and animate the change into a real Vim (tmux backend, `send-keys`) or a Neovim (nvim backend, msgpack-RPC over pynvim). Ships as a Claude Code plugin (`.claude-plugin/`, `hooks/hooks.json`, slash commands in `commands/`).

## Commands

```sh
uv sync --extra dev --extra nvim            # a bare `uv sync` leaves pytest/mypy/pynvim missing
uv run ruff check src tests && uv run ruff format --check src tests
uv run mypy                                  # bare — pyproject's files = src + tests; CI runs the same
bash scripts/full_suite.sh   # runs scripts/validate_plugin.sh first; full suite, real tmux+vim+nvim, 100% gate; 1468 tests took 27–28 min at load 7–22 (2026-10-05) — wait for load < 10, false timeouts above
uv run pytest -q -m "not integration"        # what CI runs (~1 min); coverage floor there is 98 (unit-only is ~99%)
uv run pytest -q -m "not integration" --junitxml=/tmp/u.xml && uv run python scripts/check_readme_facts.py --junit /tmp/u.xml   # facts check needs the unit JUnit; a "1100+"-style claim must be ≤ the real count and within 100
bash scripts/build_docs.sh && uv run python scripts/preview_docs.py 8000   # docs site at http://localhost:8000/vim-ai-follower/ (prod URLs rewritten to the working copy)
```

The project's bar is 100% branch coverage on the full suite; the coverage gate lives in the command line, not in pyproject. Integration tests (`@pytest.mark.integration`) need `tmux`, `vim` and `nvim` on PATH.

## Layout

- `src/vim_ai_follower/cli.py` — subcommands `start stop status hook pause interrupt speed-up speed-down toggle`; `commands.py` implements them, `keybindings.py` the tmux prefix keys.
- `hooks.py` — the hook orchestration (animate, interrupt hand-off loop, crash-fallback catch-up); `control.py` — signals + persisted pending animations (with `partial`); `binding.py` — the `session_id → (window, tmux server pid)` store that carries a session through a mid-run loss of `TMUX_PANE`; `state.py` — per-window follower state in `~/.cache/claude-vim-follower/`; `snapshot.py`/`diff.py` — before/after and the edit script; `animate.py` — tmux keystroke drivers.
- `backends/tmux_vim.py` (Vim via send-keys) and `backends/nvim.py` (Neovim via RPC) implement the `Follower` protocol in `backends/__init__.py`.
- Config: `~/.config/claude-vim-follower/config.json`; hook log: `~/.cache/claude-vim-follower/hook.log` (hooks never fail the tool call — problems go there).
- `qa/visual-battery.md` + `scripts/qa-check-N-*.sh` + `/qa-visual` — the manual visual QA battery (19 checks). `docs/superpowers/` is gitignored (private planning docs).

## Gotchas (each one cost a real bug)

- **nvim API columns are BYTE offsets** (`buf_set_text`, `win_set_cursor`). Anything typing per character must carry `col += len(ch.encode())`. In tests compare bytes: pynvim decodes with `surrogateescape`, so corruption looks like an ordinary string mismatch. The cursor the typing loop moves is the follower's window, found by handle once per line and after every pause (`_FOLLOWER_WINDOW_LUA`; dedicated: the one used last, the current one, the current tab's, any tab's, none when the buffer shows nowhere), never window 0: in an adopted nvim a user who moved to another tab or split during a pause had their own cursor moved by the resumed typing (T24a review m6, measured 2026-10-18; `tests/test_nvim_integration_pause_cursor.py`). An ADOPTED follower (`dedicated=False`, the fail-closed default; every entry point passes `_is_dedicated()`) has no fallbacks: it records the window current when `_animate_lines` starts, before the first signal check (the navigation's), uses it while it still shows the buffer and then none for good, typing by buffer handle with no cursor moved — a user who showed the follower's buffer in a window of their own during a pause and closed the follower's had their cursor dragged to the typing position (T24c review m2). An Edit types one `_animate_lines` per op, so `_run_ops` records that window ONCE, after the navigation and before the op loop, and hands it to every op (`follower_window`): recorded per op, a pause in op 1 let op 2 take the window the user left current (re-review m2').
- **nvim follower buffers are never written to disk.** Navigation must use pure API (`list_tabpages`/`win_get_buf`/`set_current_win`), never `:edit`/`:drop`/`:buffer` — those hit Vim's abandon check (E37) or silently reload from disk. `ensure_showing` is the only entry point that shows disk content; `goto_file` never does (it creates a missing buffer empty: its read-then-clear, the same `_READ_THEN_CLEAR_LUA` as show_fresh, only makes the buffer "edited" so a plain `:w` saves it). Every new tab is opened by `_show_in_new_tab`, which finds the tab by HANDLE (never window 0 after `:tabnew`: a user autocmd that jumps tabs on TabNew/BufNew/BufEnter makes window 0 the user's), gives every window that existed before the tabnew, in ANY tab, its own buffer back when an early jump (TabNew/BufNew/WinNew/BufAdd) dropped the tabnew's scratch into it (recorded by handle before the tabnew; a window the follower created is never in the record), wipes the tabnew's scratch buffer (`_wipe_if_scratch`, which first asks `buf_is_valid`: a replaced buffer may already be gone, since a start screen's `:enew` reuses the startup buffer 1 and sets `bufhidden=wipe`, and asking its name crashed every first Edit into a dedicated nvim with such a config), and turns a refused switch (E37 under 'nohidden') into NavigationFailed; a tab that fails after the tabnew (a `WinEnter * tabfirst`, a TabNew that throws) is taken back by handle (`_undo_new_tab`: every tab the tabnew added closed, hijacked windows given back, the original window current again), and a `create_buf`/naming refused by a user autocmd (a BufAdd that wipes the new buffer) is NavigationFailed, the half-made buffer wiped (`tests/test_nvim_integration_new_tab_autocmds.py`). A user TabNew that jumps to the first tab and `:enew`s there on purpose leaves the same handles as a hijack and is given back too: nothing tells the two apart (measured on nvim 0.12, 2026-10-20). Only a follower `_is_dedicated()` proves dedicated may type a first file in the current window, on BOTH backends: show_fresh opens a tab in an adopted (or state-gone) nvim or tmux Vim whatever `in_new_tab` says (tmux: `in_new_tab or self._is_adopted()`; a legacy `.pane` asked for the rename in the user's tab and turned their buffer into Claude's file; `tests/test_integration_adopted_first_file_tab.py`), because an adopted nvim's state never sets `shown_any`. On a Read it re-reads an open buffer only when CLEAN: unmodified, or its `b:changedtick` still equal to the `b:vaf_synced_tick` `_drive` stamps at a completed animation (follower text is always 'modified'); any user edit moves the tick. The stamp is one `exec_lua` (`_STAMP_IF_EXPECTED_LUA`) that stamps only when the buffer holds exactly the lines the run was meant to leave (show_fresh's typed lines, `apply_ops(before, ops)`, a resume's `partial` + remainder), so typing that lands as an animation completes is never called clean; no expected content (`before=None`, a legacy `partial=None`) means no stamp. nvim's `:edit!` of a buffer that already has a swap runs no new swap search (measured, unlike Vim), so that re-read needs no swap toggle.
- **An adopted nvim (`adopt_existing`) is never locked `nomodifiable`** — animation or navigation. Guard every lock with `if self._locks_buffers()`, which fails CLOSED: true only when FollowerState proves a dedicated follower (`_is_dedicated()` via `state.owned_state`: readable, `adopted is False`, and naming THIS follower's backend and target — a racing `stop` + `start` writes a dedicated state for ANOTHER follower), so a state gone mid-hook (a racing `stop`) locks nothing; `_exec` passes `adopted=not self._is_dedicated()` for the same reason, and a `.pane` without `adopted` reads as adopted. The same holds on BOTH backends for `close_tab` (the dedicated `bwipeout!` runs only when `_is_dedicated()`; an unknown state takes the adopted eviction rules and logs one line, since a `stop` racing a Read once wiped the user's unsaved buffer) and `user_readonly` (unknown asks; on tmux only for an answer a readonly restore requested — the `readonly-<pane>.asked` mark, consumed on read — since a state-gone hand-off sends no restore). The tmux backend locks adopted Vim like a dedicated one; that asymmetry is intentional. What differs there is the bookkeeping (the claim marks `s:release_all` gives back, the user's readonly restore, show_fresh's swap back on), and `TmuxVimFollower._is_adopted` fails closed the same way (`not _is_dedicated()`): with the state gone mid-hook, a lock sent as the dedicated one claimed nothing and the user's buffer stayed readonly after a `stop` with nothing to release it. A hook whose state is gone after it sent its lock (a Read's) or relock (`_with_unlocked`, also on an interrupt) sends `s:release_all` and takes the Vim's release mark (`_release_if_stopped`): the stop clears the state before it releases, so a hook that still finds its state was locked before any release the stop sends (`tests/test_integration_stop_mid_hook.py`, the hook held at a barrier).
- **Closing a tab in an ADOPTED editor never wipes the user's work** (eviction past `max_tabs`, and `claude-follow stop`; final review C1, 2026-10-05: a Read put the user's own modified buffer into `open_files` and five Reads later `bwipeout!` took it). tmux `s:evict` / nvim `_EVICT_LUA`: a modified buffer (nvim: not clean by `_IS_CLEAN_LUA`) is "kept"; a buffer the follower did not create is never wiped — only a window the follower opened for it is closed, and the follower's Read lock is given back (`s:release`); a clean buffer the follower created is wiped, so max_tabs still caps its own tabs; a wipe is reported only when the buffer is really gone (nvim `nvim_buf_is_valid`, Vim `bufexists()`): the cmdwin refuses `bwipeout!` with E11 under `silent!`, and the log then says "could not wipe" (review m1 of T24c; a throwing BufUnload/BufWipeout autocmd does not refuse it, measured). "Created"/"opened" are editor variables (`b:vaf_created`, `w:vaf_opened`), never cache state: they must die with the editor, or a restarted adopted Vim's buffers would read as the follower's. Dedicated followers keep the plain `s:wipe`. Vim's `getwinvar()` takes a window NUMBER in the current tab — for a window id use `gettabwinvar` over `win_id2tabwin()` (a `getwinvar(id, …)` silently read '' and closed nothing).
- **show_fresh renames only a buffer it has PROVEN is new** (final review I1: a user `BufEnter … | tabfirst` on `:tabnew` made the rename name the USER's buffer, which the landing check then confirmed, since the rename makes any buffer "the target"). tmux `s:rename`: after `tabnew`, a number above every earlier one, unnamed, unmodified — else `s:drop_fresh` and no landing (NavigationFailed). nvim `_fresh_buffer`: `create_buf` + name by handle, put in the window of the tab the tabnew ADDED (found by tabpage handle), then require it current. Never "the current buffer after `:tabnew`".
- **tmux `:tab drop` ends with `:rewind`, whose abandon check runs on the buffer it just landed on** → E37 on a dirty target; wrapped in `try/catch`. Never `:tab drop!` (discards unsaved content). Swap-file dialogs are auto-answered "edit anyway" via a scoped `SwapExists` autocmd (tmux) / buffer-local `swapfile=false` before `bufload` (nvim) — `SwapExists` does not fire under `bufload`.
- **`:tab drop` on an UNMODIFIED buffer re-reads it from disk** (its trailing `:rewind` is an `:edit`). Every completed animation ends in `:e!`, so the buffer is clean, and by `hook post` Claude has already written the finished file: an Edit flashed the final content and then typed the diff on top of it (duplicated lines, def count 1 → 3 → 5 → 3), hidden from every end-state test because the relock's `:e!` snaps it back (bug since 3923bd0, fixed 2026-09-23). tmux `goto_file` now switches to a loaded buffer by NUMBER (`win_gotoid` / `:tab sbuffer N`) and keeps `:tab drop` only for a file no buffer holds. The old reload was also silently clearing `readonly`, so the animation unlock now says `noreadonly` itself — without it, `o` on a buffer show_fresh/ensure_showing locked raises W10 and a hit-enter prompt eats the whole animation. In an ADOPTED Vim only (a dedicated follower's readonly is never the user's), the follower marks its own claim on the option in `b:vaf_ro_ours` (1 = its readonly lock, 2 = unlocked for an animation), notes the user's value in `b:vaf_user_ro` (and 'modifiable' in `b:vaf_user_ma`) before each of its readonly-changing steps while it holds no claim, and `s:restore_readonly` puts the user's back after the relock, at an interrupt and in `hand_over` (a recorded 'nomodifiable' too; the eviction's `s:release` puts back the recorded 'modifiable'). The completion relock's 'nomodifiable' on a buffer the user had modifiable is the follower's claim too (`b:vaf_ma_ours`, set by the restore only from a record): its record is kept, a later Read does not note the lock as the user's value, and `s:release` (eviction, `stop`) turns 'modifiable' back on — an Edit then a `stop` left the user's own buffer locked (E21) until `:set ma` (review I1 of T24c; `tests/test_integration_adopted_close.py` `…letting_go_after_an_edit…`). A lock option the USER changes while a claim is held becomes the record the release puts back (`s:note_user_lock`, an `OptionSet modifiable,readonly` autocmd in the adopted-only `vim_ai_follower_mode` group): a user's `:setlocal nomodifiable` under the relock claim was turned back on at `stop`. The follower's own option changes are not the user's because they all run inside the dispatcher, which sets `g:vaf_setting` around its call — so an adopted Read's lock is a call too (`s:lock`), never a typed `:setlocal` (removing the guard turns 10 integration tests red; `tests/test_integration_paste_and_claims.py`). 'paste' is GLOBAL: every unlock records the user's in `g:vaf_user_paste` (unless the run already holds it), an interrupt and `hand_over` give it back — only from that record (`s:hand_over`: no `g:vaf_user_paste`, no give-back; an adopted Vim gets 'modifiable' back only with a `b:vaf_user_ma` record), since the interrupt's paste restore (`_RESTORE_PASTE`) has already consumed it and a second give-back from no record set the user's paste to 0 — and the completion relocks give it back too (`s:lock_back`, from the record, 'nopaste' only with none; they used to turn the user's 'paste' off, sweep-5 T16), so every relock is a call now, the catch-up's plain one included (`lock_back`, no `:e!`). Never a changedtick stamp: a reload (`:checktime` under 'autoread') moves the tick but keeps the follower's readonly, and it was handed back as the user's (E45 on the cue's `:w`). The restore also writes `user_readonly`'s answer to a file, so the `:w!` hand-off cue costs no keystrokes of its own; the answer closes with the restore's six-digit token (a bare Vim number: no leading 0, which Vim reads as octal) and only the token this process sent counts, since the file is named by the pane id alone and two tmux servers can share one. `tests/test_integration_edit_no_reload.py` watches the buffer MID-animation with a VIMINIT-loaded Vim timer (no keys sent) — assert on the middle, not just the end. The completion relock's `:e!` (`s:relock`) catches what a user autocmd throws, and a BufReadPre throw leaves the buffer EMPTY (the read never ran), which locked it empty and let a `:w!` truncate the file: a buffer the relock leaves as one empty line over a non-empty file is read once more with `noautocmd`, under `shortmess+=A` since noautocmd silences the SwapExists answer too (`s:reread_quietly`; `tests/test_integration_relock_autocmd.py` `BufReadPre-throw`). The one navigation that SHOULD re-read is a Read (`ensure_showing`): it adds a clean-only `silent edit` (`s:reload`) so a file rewritten by Bash/`sed -i`/`git checkout` isn't shown stale — inside the acting call (`s:show` = `s:goto` + `s:reload` once landed), so the landing answer, and the hook's return, come after the re-read; on a line of its own after the answer, the hook returned with the stale buffer still showing (`tests/test_integration_read_reload_order.py`) — and that `:edit` re-runs the swap search and raises ATTENTION on its own when the user's Vim owns `.swp`, so it carries the same scoped SwapExists answer.
- **The tmux backend's calls are KEYED, not typed, to a Vim ready for it (T30, 2026-10-20) — its Ex logic is Vim functions defined once per Vim, and the target's path is never on a typed line.** The script maps `<F37>` (`set <F37>=\e[9087~`, a `<silent>` `nnoremap` to `<Cmd>call <SID>key(…)<CR>`, `:<C-u>call` before patch 8.2.1978) and writes `ready-<server pid>-<pane>` (`<dispatcher> <vim pid>`; VimLeave removes it, `_sweep_mode_files` removes a dead pid's), trusted only when written no earlier than that Vim's start minus 2 s (`_process_started`, `ps -o etime=`: a reused pid's old file named a Vim that never sourced the script), and a Vim that never gets ready is waited for once per pane process (`unready-<pane>` holds the pane pid); `_send` then writes each call as a Vim list to a call file `k<8 digits>` (`_call_file`, exclusive, unread ones swept after 600 s; a plain `:` line goes as `['ex', …]`) and sends ONLY `<F37>` + the digits + `<F37>` as raw bytes (`send_hex`), which `s:key` reads with `getchar(0)` (0.2 s at most, any other key aborts), so nothing reaches the command line: 0 of ~410 calls echoed, dedicated and adopted, idle and under `load_burn.sh 8` (`scripts/measure_typed_echo.py`, before: 1/408 adopted over 1 ms). The define line is typed once per Vim (`_define` skips it when `_vim_ready`), its guard `maparg('<F37>')` for a ready Vim and `exists('*Fn')` for any other; it comes back only when the last keyed call (`keyed-<server>-<pane>`) is still unread 1 s after it was sent and after the ready file was written (`_keyed_call_unread`). So a user's `:mapclear` costs one lost call — its navigation fails and the pane backs off, as for a Vim that does not answer — and the first contact after the backoff re-sources (`test_a_vim_whose_call_key_mapping_was_cleared_gets_it_again`); typing the define at once was rejected, since a lost mapping and a Vim blocked in `:!make` look the same, and keys typed into the latter go to the command's stdin. A Vim with no `TMUX_PANE` (`env -i`), on another HOME or without +eval never writes a ready file and is typed its calls exactly as below. Unit tests stand in a never-ready Vim (conftest `calls_typed_without_a_vim`; `@pytest.mark.real_call_key` opts out). For the typed path: Vim echoes every typed command on its command line: the demo flashed the absolute path on every edit (2026-09-29), and later a 12–30-row block of Vim script (the ~1,500-character goto line, 2026-10-05). The logic lives in `tmux_vim._VIM_SCRIPT` (legacy Vim script, every function `abort` so an error stops it where it used to stop the rest of a typed line, helpers script-local, ONE global dispatcher `VafFollower_<6 hex>` named after a hash of the script + cache dir), written to `CACHE_DIRECTORY/vaf-<hash>.vim` (the dispatcher is defined only once every `s:` helper and the preamble's `s:dir` exist, because `:source` carries on past an error under `sil!`; `_script_file` touches the current script on every define, and `_sweep_scripts` deletes the cache dir's other scripts unused for seven days (Alberto's A7: an older plugin version never touches its script) and cut-off `.vaf-*.vim.<hex>` temporaries older than 600 s — no Vim needs a script it already sourced, only the next define of a Vim that lacks the dispatcher reads it) and sourced by `_define_line` (`:if !exists('*VafFollower_…')|sil! so ~/.cache/…|endif`), which every entry point that may be first sends before its calls — so a Vim that lost the functions (`:delfunction`, an adopted Vim restarted in the same shell: same pane pid) gets them on the very next call; the script deletes older dispatchers, but only one Vim says was set from `vaf-<its own hash>.vim` in THIS cache dir (`:verbose function`'s path — its words are translated — compared with `fnamemodify(resolve(…), ':~')`, because Vim records a script symlink-resolved and shows it `~/…` under its HOME; a literal `s:dir` match never fires), so a user's own `VafFollower_123abc()` survives, even from a file named `vaf-123abc.vim` elsewhere, and a hand-pasted dispatcher (no file) is the user's code and stays; a dispatcher of ANOTHER follower cache dir (another HOME spelling) goes only once its `claude-vim-follower/vaf-<its hash>.vim` no longer exists (swept). The script carries no `scriptencoding`: under `LANG=ja_JP.SJIS` (`encoding=sjis`) `scriptencoding utf-8` turned every backslash into `?` (U+005C has no Shift-JIS code) and no dispatcher was ever defined; the template is ASCII, pinned by a unit test. Each call line is `:if exists('*Fn')|call Fn('op',…)|endif`, no spaces around the bars: two screen rows at 49 columns is ≤ 97 typed characters with the `:` (96 from `getcmdline()`; measured on Vim 9.2, `:` + 97 puts the cursor on a third row), the longest is show_fresh's rename, whose handle carries the pane id, and it must fit up to six-digit pane ids (pinned by `tests/test_integration_cmdline_paths.py` and the unit `test_every_typed_call_fits_two_screen_rows`), so a Vim without them runs nothing and raises no E117. A path reaches Vim through a handle file per call (`_path_handle`, `p<pane>-<6 hex>`, also the call's token): `s:read` reads it byte-exact (`filereadable()` + `readfile(…, 'b')`, never a try around the read) and `delete()`s it (never a fixed per-pane file — Vim runs a line after the send returns, so an eviction and the next pre-wipe would share it; unread handles are swept after 600 s, any pane's). A missing handle reads as '' and every function then acts on nothing; a call that must ACT (`s:goto`, `s:rename`) is followed by an Escape pair and a separate `s:landed` call (never the acting call's tail — a goto that opens a second tab from one leaves a prompt that swallows the next line's first screen row) that answers `landed-<pane>.txt` only when the current buffer is the one the acting call recorded landing on (`g:vaf_landed`, by NUMBER, next to the token `g:vaf_k`), and Python sends nothing more without it (`NavigationFailed`, which the hooks log in one line and skip the edit, marking the file stale) — a failed goto once let a Read lock, and an Edit's relock `:e!` wipe, the user's own unsaved buffer. Never confirm by re-deriving the target's NAME: Vim navigates by file identity (`:tab drop` lands on an existing buffer opened through a file symlink, e.g. a dotfiles `~/.vimrc`, or under a case variant on macOS), and a name check failed every Read of such a file after 10 s. The script names the cache dir in full (`s:dir`; a file, never echoed), so only the define line types a path: `~/.cache/…` when the pane's Vim shares the hook's HOME — asked once per pane pid (`_vim_shares_home`, `:silent! call writefile([], expand(…, 1))`; the `1` (nosuf) is load-bearing, since a `wildignore=*/.cache/*` makes a plain `expand()` return ''; `:source ~/…` itself ignores 'wildignore', measured; an adopted pane's pid is the user's SHELL, so no answer with the path handle still unread drops a "yes" and the next call asks again), else the absolute path (through `fnameescape()` unless it is plain); when the guarded absolute form passes 97 characters (117 for a plain `/Users/…/.cache/…`), the guard is dropped (`:sil! so <path>`, re-sourced on every call, ~0.2 ms; the script keeps no state of its own beyond the mode file's `s:mode_written`/`s:mode_timer`, which a re-source only resets (one extra write) — and its body is wrapped in `if 1`…`endif`, because a Vim without +eval, e.g. vim-tiny, runs every function BODY as top-level Ex commands and empties the user's buffer; `tests/test_tmux_typed_path.py` proves it in Docker), and past an 88-character script path the guarded form stays and logs it once per pane (`define-rows-<pane>`, marked used on every such line and swept a day after last use, like old scripts). Commands that print a file's name are `silent` (`:file`, `:tab drop`, `:tab sbuffer`), errors still showing. `tests/test_integration_cmdline_paths.py` logs every `CmdlineChanged` plus `:messages` — never pass `_vim_string(file_path)` into a typed line.
- **Every typed line and its Enter go in ONE `send-keys` (`TmuxPane.send_line`: the CR inside the `-l` text).** Since T30 that is the define line, the HOME question, animate's paced `:N`/`:Nd`, and every call to a Vim not ready for the call key (above); a keyed call types nothing. With the Enter in a second subprocess Vim drew the line, flushed and waited for it: measured 2026-10-17 from Vim's raw terminal output (`pipe-pane` into a timestamped recorder, 49 columns, 400 calls), every line stayed on screen 3–64 ms (median 6 ms, 15 ms under load; a canary with a 50 ms gap read 55–150 ms); in one write Vim reads both and executes before it flushes, so the line's bytes still reach the terminal but in the same write as the redraw that replaces it — 1–3 of 400 still showed for over 1 ms (1.5–64 ms, the longest under load), each one a line Vim read in two parts. Never join the Enter as `\; send-keys Enter` (the semicolon rule below). **And a line that has RUN stays drawn**: Vim leaves a typed Ex command on its bottom row until something redraws it, which the input-gap measurement cannot see (review I1 of T23: `:setlocal readonly nomodifiable` after every Read; in a pane wide enough for a call to fit one row, 12 of 12 calls, adopted Vims included; `goto_line`'s `:N` everywhere). The dispatcher ends with `redraw` + `echo ''`, and so does every plain line that can be the last one an entry point types (`_cleared`, `_CLEAR_COMMAND_LINE`): `redraw` alone keeps the line, a bare `echo ''` after a command that printed raises a hit-enter prompt (`:1|echo ''`, since a range before a bar PRINTS the line — so goto_line types `:exe N`), `redraw!` repaints the screen. An adopted Vim's plain relock skips the tail (the readonly restore, a call, always follows, and the claim plus the tail passes 97 characters). `tests/test_integration_command_line_clear.py` reads the bottom rows 300 ms after each call at 49 and 200 columns. Unit tests see each line as `send_text` + `send_key("Enter")` through conftest's `typed_lines_as_text_and_enter`; `@pytest.mark.real_send_line` opts out, and `test_no_typed_line_waits_for_a_separate_enter` runs every entry point that way, completed and interrupted, dedicated and adopted. animate.py's paced `:Nd`/`:N` + Enter pairs stay separate on purpose (they are the visible animation).
- **tmux ends a command at ANY argument that ends in `;`, and drops that `;`** — so `send-keys -l -- 'int a = 1;'` types `int a = 1`, a lone `;` types nothing, `c;;` types `c;`, and a final `\;` types `;` (where the `;` is dropped, a backslash left at the end becomes the `;`). - **A CRLF file is `fileformat=dos` in both editors: its buffer lines carry no CR** (`buffer_forms` accepts that form). Dos means every LF ends a CRLF, whatever the last line does: `a\r\nb` (no final EOL) loads as dos `['a', 'b']`, `a\r\nb\r` as dos `['a', 'b\r']`, a lone `a\r` as unix (measured on Vim 9.2 with `-N` — `-u NONE` alone is 'compatible', empty 'fileformats' — and nvim 0.12); `diff.file_lines` once required every LINE to end in CR, so a CRLF file with no final EOL was typed with its CRs into a dos buffer and the save wrote `\r\r\n` (final review of backlog-sweep-5, C1; the `no-final-eol` cases of `tests/test_integration_crlf.py` and `tests/test_nvim_integration_crlf.py`). An Edit that changes only the line endings types nothing, so nvim's 'fileformat' follows the file on disk at a completed animation (`_format_from_disk`: all CRLF → dos, all LF → unix, mixed → left as loaded), adopted buffers included, as 'bomb' does; tmux gets it from the relock's `:e!`, and a Read's re-read detects it in both. Setting 'fileformat' or 'bomb' marks an nvim buffer modified, so `_format_from_disk` puts an untyped buffer that was clean and now holds the file back to unmodified (an endings-only Edit left a clean adopted buffer `[+]`). The hand-off wait compares the file's RAW bytes with `raw_after`, the bytes Claude wrote (two undecodable bytes decode alike). MIXED endings load as `fileformat=unix` with each CR kept in its line (`^M`), and `buffer_forms` accepts only that: the CR-stripped form is what the follower's own retype left before T24, but it is also what a user's `:%s/\r$//` leaves, and a tmux probe that said "holds" for it let the relock's `:e!` discard that unsaved edit (T12+T13 review I1). No probe accepts it: lines the follower types into a mixed file carry their CRs since T24, so `typed_form` is always one of `buffer_forms` (pinned by `test_the_typed_form_is_always_one_of_the_buffer_forms`; nvim's probe had a clean-or-dedicated exception for the stripped form, removed as dead in sweep-5 T31), and nvim's `_format_from_disk` sets 'fileformat' unix for a mixed file whose buffer holds those lines. An Edit that leaves a CRLF (dos) buffer's file MIXED is the one exception to typing a mixed file's CRs: a line typed with its CR into a dos buffer writes it doubled, and every kept CRLF line differed from its base and was retyped, so an interrupt handed over a buffer whose `:w` wrote `\r\r\n`; the diff types `backends.typed_onto(before, after)` instead (the dos form, `dos_lines`: one insert for one new line), and the completion gives the buffer the file's own lines — tmux's relock `:e!`, nvim's `_format_from_disk` (`buf_set_lines` + 'unix', returning the lines `_drive` stamps) (`test_an_edit_that_makes_a_crlf_file_mixed_types_no_cr_into_its_dos_buffer`, `test_a_crlf_file_an_edit_makes_mixed_saves_claudes_bytes`).

- Test-side: assert on the specific call, not `assert_called_once` — exact call counts break whenever a neighbor adds an API read.
- **Run the full suite alone.** Integration tests spawn real tmux servers and nvims; two suites in parallel (or a parallel agent's) push load past 10 and produce false timeouts — rerun the failing test alone before calling it a regression.
- **QA scripts (`scripts/qa-check-*.sh`) must run from inside a tmux pane** (`$TMUX_PANE` guard) and background a hook with `> log 2>&1 &`, never `| tee` — a pipe makes the shell wait and the interrupt/pause you're testing never lands. Finish with `source scripts/qa-lib.sh && qa_teardown`.
- **`conftest.py`'s autouse `no_pid_ancestry_walk` only reaches IN-PROCESS code.** It stubs `session._tmux_panes_by_pid` so the suite doesn't resolve to whatever window the developer is sitting in — but a test that runs the hook as a SUBPROCESS bypasses it and the pid walk hits the real tmux server. Point such a test at a private socket and fire the blind half from the pytest process, not from inside a pane, or it passes for the wrong reason. Opt in with `@pytest.mark.pid_walk`.
- **`tmux` and `keybindings` share one `subprocess` module object**, so patching `vim_ai_follower.tmux.subprocess.run` silently intercepts `keybindings`' `git rev-parse` too. Resolve any expected path INSIDE the patch, or expectation and code under test see different worlds.
- **Coverage is blind to subprocess execution**, so the e2e CLI tests add none — expect the percentage not to move, and never chase it with `# pragma: no cover`. To read a real buffer from an integration test, dump it with Vim's `writefile()` (or `buf_get_lines` over RPC): delete the dump first and wait for a sentinel prefix so a stale or half-written read can't pass for an answer, and retry — a loaded machine swallows the ESC pair.
- **Worktrees:** tool-created worktrees may start from a stale `origin/main` — check `git rev-parse HEAD` against local `main` first. `docs/superpowers/` is gitignored, so edits made there inside a worktree never come back via merge: copy them to the main checkout before removing the worktree.

## Release

`claude plugin update` is gated on `.claude-plugin/plugin.json`'s `version`, not on git. Every user-visible fix: bump the version, commit, then `claude plugin tag --push` (creates `vim-ai-follower--vX.Y.Z`; refuses a dirty tree — never `--force`). CI is `ci.yml` (unit suite + coverage floor) and `lint.yml` (ruff + mypy); the README coverage badge is static — update it in the same commit when the measured number moves.

- `scripts/validate_plugin.sh` (run first by `full_suite.sh`, skipped without `claude` on PATH) is `claude plugin validate --strict .` tolerating exactly one warning: "CLAUDE.md at the plugin root is not loaded as project context" — this file is the repo's notes for Claude Code, not plugin context, so it stays. Any error or other warning fails. Not in CI: it needs the Claude Code CLI.
- `git fetch` before pushing main: Dependabot/deps PRs merge on GitHub (`uv.lock` bumps), so origin/main moves without you; merge it, rerun lint + unit on the merged tree, then push.
- `docs.yml` builds with `uv run`, and `[tool.uv] python-preference = "only-system"` + `.python-version` (3.14) means the job must install THAT Python (`python-version-file`); with 3.11 every `uv run` failed. Pages is enabled with `gh api -X POST repos/albertosca/vim-ai-follower/pages -f build_type=workflow` (done 2026-10-05).
